# ミニアプリの全体設計

各Appが自分の仕様・実装・テーブル・テストを管理し, 公開APIで連携する.

## 所有境界

| App                                               | 所有データ・責務                                                         | 公開する機能                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------- |
| [認証・アクセス管理](../app/auth/README.md)       | アカウント・認証情報・ロール・会員紐付け・開発版検証者の管理             | 認証, 現行権限・代理操作対象の確認             |
| [ポータル](../app/portal/README.md)               | App一覧・入口設定. 初回は業務・監査・ジョブ実行テーブルを持たない        | 各Appへの遷移                                  |
| [名簿](../app/roster/README.md)                   | 会員名簿・級履歴・名簿取込と変更履歴                                     | 現役会員検索, 最小限の基本情報, 指定日時点の級 |
| [練習](../app/practice/README.md)                 | 会場・練習・出欠・練習監査と集計                                         | 権限に応じた練習・登録状況                     |
| [大会参加希望](../app/tournament-entry/README.md) | 一般会員の参加希望と変更履歴. 詳細は後続設計                             | 許可された大会班向けの参加希望取得             |
| [大会班](../app/tournament-operations/README.md)  | 大会・募集条件, 受付後の業務状態, 確定名簿, 戦績・カウント・作業タスク案 | 募集情報, 会員向けに限定した処理結果           |

複数Appが利用するデータにも正本の所有者を1つ定める. 他Appによる私有テーブルの直接参照・更新, 横断JOIN, 内部型・内部実装のimportを禁止する. App間のIDは公開契約上の参照であり, 横断外部キーや連鎖削除を前提にしない.
具体的なテーブル・所有者は[DB設計](data-design.md)を正本とする. 監査・実行記録もそこで定義した所有者の名前空間に置く. 運用基盤はジョブ全体の進捗を保持できるが, 共通の業務データ置場にはしない. [SCR-OPS-01](screens-and-flows.md#scr-ops-01)の横断運用画面は所有Appの運用APIを集約する別の運用機能として扱い, ポータルへ削除・集計ロジックを置かない.

## 許可する依存

- 全Appは認証の公開契約を利用できる. 各Appが最終的な業務認可を行う.
- 認証は名簿の候補検索・存在確認を利用する. 名簿は認証から検証済み主体を受け取る. 相互のAPI呼出しが再帰しないよう, 主体検証と会員照会を分離する.
- 練習と大会の各Appは名簿の公開契約を利用する. 名簿は練習・大会の内部を知らない.
- ポータルは公開入口と必要な概要APIだけを利用する. 他Appはポータルの内部状態に依存しない.
- 大会2Appの依存は[大会契約](../contracts/tournaments.md)に限定する. 練習と大会の間に初回の依存は設けない.
- 共通UI, 汎用日付処理, 契約型は共有可能. 締切・対象級・状態遷移等の業務判断は所有Appに置く.

## 実行環境とDB

Supabaseは共通のアカウントで管理する. 開発・本番は環境仕様に従い別プロジェクトとし, 各環境内でglobalとApp localを区別する. ミニアプリごとにSupabaseアカウントや物理DBを増やすことは要件としない.
`global`は複数App向けの正本, `auth_local`, `roster_local`, `practice_local`, `tournament_entry_local`, `tournament_operations_local`は内部テーブルのスキーマ名案. 具体的な分類は[DB設計](data-design.md)に記載する.
globalの各テーブルも管理責任は1つのAppに属する. 定義・マイグレーション・書込API・入力検証・保持期限・テストをそのAppに置く. globalは全Appによる直接更新や全項目公開を意味しない. localの結果をAPIで提供しても内部テーブルをglobalへ変更する必要はない.
HTTPかプロセス内呼出しかに依存しない公開契約とする. 同じ所有Appが管理するglobalとlocalは同一トランザクションで更新できる. 例えば名簿Appはglobal.membersの現在級とroster_local.grade_historyを原子的に更新する.
App内の変更はそのAppの仕様・テスト・公開契約だけで判断できることを目標とする. 契約変更時だけ利用Appへの影響を確認する. 全Appへの全権DB資格情報の配布で境界を代替しない.

## 画面遷移

URLの名前空間案は `/auth`, `/portal`, `/roster`, `/practice`, `/tournament-entry`, `/tournament-operations`. 各Appが画面・ナビゲーション・入力途中の状態を所有し, ポータルへ戻るリンクを提供する.
直接URLを開いても利用できる. 未認証なら認証へ遷移し, 検証した同一システム内の戻り先へ復帰する. 戻り先URL・対象会員IDを認可根拠にしない. 認証復帰後も各Appが権限と対象会員を再検証する.
操作対象会員の引継ぎは初期表示のヒントに限定する. 各Appで対象氏名を表示し, 送信時に再検証する. ポータルのリンク非表示は認可の代わりにならない.
画面と所有Appの対応は[画面一覧](screens-and-flows.md)に記載する. 大会2Appの画面IDは後続で定義する.

## 整合性・停止・削除

同一App内の更新と監査はローカルトランザクションで確定する. App横断の原子性は暗黙に仮定しない. 認可・会員資格の確認と更新の間の競合について, 公開境界を維持した同一DB内の原子的な検証, または版付き検証等を実証し方式をレビューする. 単なる事前API照会だけで[TST-SYS-04](../tests/integration/specification.md#tst-sys-04)等を満たしたと判断しない. 権限剥奪後の次の操作を拒否する既存要件は維持する.
必要な認証・名簿APIが失敗した場合は成功扱いにせず, 業務更新を確定しない案. 表示用キャッシュを権限判定に流用しない. 名簿APIが級を「不明」と返した場合と通信失敗を区別し, 通信失敗を不明級として集計確定しない.
月次処理の順序・参照整理・失敗時の再開, バックアップの保存・復元要件は[保存期限](data-retention.md)を正本とする. 各Appは運用APIを公開し, 他Appのテーブルの直接削除や共通基盤からの境界迂回を許可しない.

## 文書とテスト

`app/<app>/docs/`に内部仕様, `app/<app>/tests/`に固有テスト, 実装時には同じApp内にsrcとDBマイグレーションを置く. `contracts/`は公開契約だけを置き, 業務実装や共有DBモデルを置かない.
`documents/`は全体方針, 共通運用, 工程と索引. `tests/integration/`は横断契約・整合性, `tests/e2e/`はAppをまたぐ利用シナリオ. 各Appは他Appの契約スタブで単体実行でき, 契約適合性は別途提供側・利用側で検証する構成を目指す.

## 配信単位と版管理

初回のVercel配信単位とGitブランチ・環境の対応は[環境仕様](development-environment.md#gitとvercelの環境対応)に従う. 同じビルドへ同梱してもAppの所有境界と公開APIを維持する. 操作別の入出力・認可・連携順序は[API索引](../contracts/README.md)を正本とする.
