# 開発版・本番版の提供とバージョン管理

本番環境と分離した開発環境を提供し, 本番公開後も継続して利用する.

## 提供範囲

- 運営者と指定検証者がスマートフォンからアクセスできる専用のHTTPS URLを提供する.
- [MIL-SYS-03](scope-and-milestones.md#mil-sys-03)でLINEログイン・ポータル・自己申告紐付け・権限確認, [MIL-SYS-04](scope-and-milestones.md#mil-sys-04)で名簿, [MIL-SYS-05](scope-and-milestones.md#mil-sys-05)で練習出欠を順次提供する. 未提供機能を利用可能と表示しない.
- 本番公開後も開発版を維持し, 次の変更を確認できるようにする. 同じコードを用い, 設定と接続先を分ける.
- ログイン前後の全画面で「開発版」を明示し, 確認用データであることと初期化の可能性を案内する.
- 検証者の許可リストをサーバー側で確認する. 業務ロールと会員紐付けによる認可も適用する. URLを知っているだけでは業務情報を閲覧できない.

## 環境分離

| 対象                 | 方針                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| Web・DB              | 開発専用URLと独立したSupabaseプロジェクトを使用. 本番DBへの資格情報を開発側へ渡さない                          |
| LINE・LIFF           | 開発専用チャネル・LIFF・コールバックURLを設定し, 指定検証者の実機ログインを実証                                |
| セッション・秘密情報 | Cookie・署名鍵・トークン検証対象を環境別に分離. 別環境の認証情報を受理しない                                   |
| GAS・バックアップ    | プロジェクト・保存先・資格情報・定期処理を分離. 開発版の削除・復元が本番に影響しない                           |
| データ               | 架空の名簿・家族・練習を使用. 本番データを自動複製しない. 実機ログインで必要な検証者のLINE識別情報は最小限保持 |
| 初期化               | 開発環境限定の管理手順とし, 対象確認・検証者への案内後に実行. 一般利用者には許可しない                         |
| 保持期限             | 開発版にも保存期限一覧を適用. 本番由来データを使う移行検証は利用範囲・保存先・削除手順を別途レビュー           |

設定の不足・不整合時は処理を拒否し, 本番設定へ自動で切り替えない. 開発版のポータルには本番業務Appへのリンクを既定で置かない.
開発・本番を合わせてランニングコスト0円の成立を確認する. ホスティングは下記のVercel構成案とし, 無料枠の適用可否, 定期処理, 停止・再開条件は未検証.

## 受入条件

1. [MIL-SYS-03](scope-and-milestones.md#mil-sys-03)完了時, 指定検証者が専用URLから実機でLINEログインし, 紐付け・ポータル操作を行える.
2. 未指定者の業務情報アクセスと, 指定者のロール・紐付け範囲外の操作を拒否する.
3. 開発版の登録・更新・削除・バックアップ・復元・初期化が本番データや保存先へ影響しない.
4. 全画面で開発版と分かり, [MIL-SYS-04](scope-and-milestones.md#mil-sys-04)・[MIL-SYS-05](scope-and-milestones.md#mil-sys-05)の機能を順次確認できる. 本番公開後も利用できる.
5. 設定・更新・検証者追加/解除・初期化・停止/再開の手順を用意する. 秘密値は文書へ記載しない.
6. 開発版を含む無料運用の成立条件を記録し, 更新時には型チェック・単体・結合・主要E2E・ビルドを通す.

## GitとVercelの環境対応

作業ブランチの命名, PRの反映経路, 緊急修正, 人間とAIのGit操作範囲は[Git運用規約](git-workflow.md)に従う.

初回はApp境界を保った1つのWebビルドを1つのVercelプロジェクトで配信する案とする. 各Appのコード・契約・テストは同じリポジトリ内の所有ディレクトリで管理する. App単位の独立デプロイは初回必須にせず, 将来分割する場合は契約版の組合せと環境内URLを別途管理する.

| 用途               | Gitブランチ   | Vercel環境        | 利用入口・接続先                                                          |
| ------------------ | ------------- | ----------------- | ------------------------------------------------------------------------- |
| 本番版             | `main`        | Production        | 本番用の固定URL. 本番Supabase・LINE・LIFF・GASへ接続                      |
| 継続提供する開発版 | `develop`     | Preview           | developのブランチURLを固定入口にする. 開発Supabase・LINE・LIFF・GASへ接続 |
| 個別変更の確認     | `feature/*`等 | Preview           | デプロイごとの確認URL. 継続提供する開発版とは区別. 本番資格情報を渡さない |
| ローカル           | 作業ブランチ  | Local Development | 開発専用または隔離テスト設定. 公開する開発版とは区別                      |

VercelはPreviewとProductionを提供し, ブランチ別設定による継続的な検証環境を構成できる. Custom Environmentの作成を必須にしない. 新規プロジェクトの初回デプロイはProductionになるため, 開発ブランチを選ぶだけでPreviewになるとは扱わない. 初回セットアップで実際の対象環境・接続先・公開状態を確認する. [公式の環境仕様](https://vercel.com/docs/deployments/environments)

ブランチURLは更新される入口, デプロイ固有URLは特定の成果物を調べるための参照として使い分ける. URLだけをリリース番号とみなさない. 開発版のLINEコールバック・LIFFには固定入口を登録し, 個別PRの可変URLを無条件に追加しない. [公式の生成URL仕様](https://vercel.com/docs/deployments/generated-urls)

開発版と本番版は同時に利用可能とし, 開発版更新で本番版のURL・設定・成果物を変更しない. 本番リリース後もdevelopと開発版入口を維持する. VercelのDeployment Protectionとアプリの検証者許可リストは別の制御である. 実機のLINE内ブラウザから指定検証者が入れることを先行実証し, Vercel側の保護だけで業務認可を代替しない.

## バージョンの識別と記録

Gitはソースの履歴, Vercelは環境別のデプロイ履歴として併用する. 開発版と本番版は異なる版で稼働できる. リリース番号をブランチ名だけで代替しない.

| 項目         | 管理方法                                                                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ソース版     | 本体実装時にルートのpackage.jsonのversionへ`MAJOR.MINOR.PATCH`を記録. 互換性を壊す変更・機能追加・修正で更新する. 本文の例は採番規則であり, 現時点のリリースではない |
| 本番表示版   | 例: `1.2.0`. 環境名とGit SHA短縮値を併記                                                                                                                             |
| 開発表示版   | 例: `1.3.0-dev.<shortSHA>`. 元のソース版, Git SHA, デプロイIDを保持し, 同じコミットの再デプロイも区別                                                                |
| ソースの特定 | デプロイ元Gitコミットの完全SHAとブランチ. リモートへ未反映の作業ツリーから本番配信しない                                                                             |
| 成果物の特定 | Vercelプロジェクト, 対象環境, デプロイID, 固有URL, 作成日時, 配信中の固定URL                                                                                         |
| 互換性       | API契約の対応版, DBマイグレーション版, 非秘密の設定改訂番号                                                                                                          |
| 検証・切戻し | チェック結果の参照, 確認者, 配信開始日時, 前回正常版, 切戻し可否・条件                                                                                               |

ソース版はGit, デプロイIDと成果物はVercel, 両者の対応と配信・切戻しの判断は環境別の運用記録に保存する. 記録はデプロイ処理の出力を基に作成し, まだ存在しないデプロイIDをソースへ埋め込んで循環を作らない. Vercelの保持期間だけに過去のリリース証跡を依存させず, 非秘密の記録を運用者が管理する. 保存先・保存期間は運用開始前に確定する.

アプリにはビルド時のソース版・SHA・環境を渡し, 設定が欠ける場合は本番用の既定値で補わずビルドを失敗させる. 画面の共通フッターで環境・表示版・SHA短縮値を確認可能にする. デプロイID等の詳細は運用者が確認できる場所に置く. 秘密値・接続文字列は表示や記録に含めない. 環境表示はログイン前から有効にし, 実行環境の設定を正本にする.

製品表示の例は「開発版 1.3.0-dev.abc1234」「本番版 1.2.0」. 開発画面には「開発版です。データは初期化されることがあります。」と案内する.

Gitタグ・Releaseの作成を版管理の前提にしない. Git初期化とinitial commitは今回の明示指示に基づく初回作業とし, 以降のローカルコミットはcommitスキルに従う. リモート設定とマージは人間が行う. AIによるgit pushは `/git-push` スキル経由に限定し, PR作成は許可する. 操作範囲は[Git運用規約](git-workflow.md)に従う.

## 更新・切戻し手順

1. 人間がGitリモートとVercelプロジェクトを関連付け, Production Branchをmainに設定する. 本番設定はProductionのみ, 継続開発用設定はPreviewのdevelopに割り当てる. 他ブランチに開発用の特権資格情報を一律配布しない.
2. 開発環境で型チェック・単体・結合・主要E2E・ビルドを通し, 対象SHA・ソース版・契約版を記録する.
3. 人間によるdevelopへの反映後, VercelのPreviewで対象SHA・環境変数・DB・LINE・固定入口を確認し, 開発版の更新記録を残す. 設定変更も新規デプロイで適用し, 前のデプロイと区別する.
4. 本番へ反映する内容をレビューし, main上の対象SHAでチェックを通す. 開発と本番でマージによりSHAが異なる場合は差分と検証結果を対応付ける. 本番用設定でビルドし, DB変更との互換性を確認する. Previewの成果物を環境確認なしに本番へ転用しない.
5. 人間が本番への反映を行い, 配信URL・環境・版・主要画面を確認して配信記録を確定する. mainへのpush/mergeに連動して本番デプロイされる設定では, その反映を公開操作として扱う. 同時に開発版の利用継続も確認する.
6. 問題発生時は対象環境・前回正常版・DB/API/設定の互換性を確認して切戻しを判断する. 本番は利用プランで可能なVercelのRollback, または既知のGit版からの再デプロイを使用し, 新たな配信記録を残す. 開発版は既知の版からPreviewを再デプロイし, developの固定入口の指す先も確認する.

VercelのRollbackではDB・外部サービスの状態が自動で戻るとは扱わない. 旧アプリと現在DBが非互換なら, 受付停止や前進修正等を選び, バックアップによる無条件上書きは行わない. 使用可能なRollbackの範囲はプランと設定に依存するため, 実設定で確認する. [公式のRollback仕様](https://vercel.com/docs/deployments/rollback-production-deployment)

## 無料運用と未検証事項

VercelのHobbyは個人・非商用利用向けであり, 本プロジェクトの団体利用が適合するかを運用者が確認する. 無料運用は確定扱いにせず, Supabase・LINE・GASも含む利用条件, 容量, 定期処理, 停止条件を先行実証で記録する. [公式のHobby仕様](https://vercel.com/docs/plans/hobby)

この文書は提供・版管理の仕様であり, Git連携, Vercelの設定, デプロイ, LINEのコールバック設定は未実施. 本体コード・実行可能なアプリテストも未実装. [環境の結合試験](../tests/integration/environments.md)と[開発版・本番版のE2E](../tests/e2e/specification.md#ete-env-01)で実装後の受入を確認する.
