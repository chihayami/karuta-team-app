本書を保持期限・削除条件・バックアップ運用の正本とする. テーブルの区分・所有者・列定義は[DB設計](data-design.md)を参照する. 以下は同じglobal/local分類に沿って, テーブル内の対象行・列ごとに保持規則を対応させた一覧である. 同じテーブルに複数の規則があることは, 別テーブルへの分割を意味しない.

## テーブル以外の保持規則

| ID                                | 対象                        | 保存期限・起算点 | 期限後の処理・状態                                       |
| --------------------------------- | --------------------------- | ---------------- | -------------------------------------------------------- |
| <a id="ret-ops-02"></a>RET-OPS-02 | 取込CSV・出力の一時ファイル | 処理完了まで     | 即時削除. 利用者が持ち出したファイルの管理手順は別途     |
| <a id="ret-ops-03"></a>RET-OPS-03 | アプリログ                  | 記録から15日     | 期限に従い削除. トークン・氏名・自由記述は原則出力しない |

バックアップ・作業コピー・復元DBは下記の規則に従う. 作成しないinvitationsやpractice_summariesは保存対象に含めず, [DB設計](data-design.md)に不採用として記録する.

監査の記録内容は[操作履歴の列定義](operational-data.md)に従う. 氏名・自由記述の本文を保存しないことを理由に履歴の期限を延長しない. 練習・出欠に結び付く操作はRET-PRC-05, 会場単体の操作はRET-PRC-06を適用する.

## 期限の境界

[RET-PRC-02](data-retention.md#ret-prc-02)・[RET-PRC-04](data-retention.md#ret-prc-04)・[RET-PRC-05](data-retention.md#ret-prc-05)では開催月をN月としてN+2月1日に削除する. 本番・バックアップとも同じ期限を適用する.
例: 2026年1月1日〜31日の練習は2026年3月1日, 2026年12月の練習は2027年2月1日に削除する.

年単位の保持は, 1日00:00の日本時間で年数経過済みのものを削除する案.
例: 2026年10月8日退会は2029年11月1日, 2026年10月1日退会は2029年10月1日を削除日とする案.
解除・監査履歴の1年も同じ判定を使う. 月初当日の周年日を含むかと, うるう日の周年日の扱いは[DEC-OPS-02](open-questions.md#dec-ops-02)で物理設計前に確定する.
削除ジョブが失敗した場合も期限経過情報は通常APIから返さず, 削除完了とは扱わずに再実行・失敗報告する.

## 集計化と識別情報の整理

練習の集計列・基本属性・NULL制約・会場名の固定と, 個人別出欠の削除を伴うトランザクションは[練習Appのデータ設計](../app/practice/docs/data-design.md)に記載する. 保持対象と削除対象の期限は上表に従う. 操作者情報は現在の列定義では出欠と監査に存在し, practice_sessionsに未定義の操作者列を想定しない.

退会者名簿はglobal.membersの在籍状態で通常名簿と分けた専用画面・ビューとして提供する案. テーブルを物理移動せず会員IDと既存参照を維持し, 最終削除は実データに対して行う. 氏名を複製しない級履歴もmember_idで名簿に結び付く個人別履歴であり, [RET-RST-02](data-retention.md#ret-rst-02)に従う.

退会者名簿の削除では参照元も確認する. 紐付けや監査の未経過期限を理由に氏名等を延長保存しない設計とし, 参照の解除・削除を同時に行う案. 認証API経由で対象会員の紐付けを整理する. 他会員への有効な紐付けや保護者アカウントは連鎖削除しない.

[RET-AUT-01](data-retention.md#ret-aut-01)・[RET-AUT-02](data-retention.md#ret-aut-02)では利用終了判定・判定日の記録・再有効化時の判定日解除・定期削除を実装しない. 自動削除を前提にした再登録可否の検討も対象外. 紐付け・ロール・セッションの有効性は操作時に確認する. アカウント保持を理由に, 名簿・級履歴・解除済み紐付け・監査・セッションの期限を延長しない.

## バックアップと復元

全DBを対象とし, GASとスプレッドシートを主な保存手段とする. 24時間間隔, 保存期間15日, 確認担当者は全体管理者. 復元目標時間と許容損失は[DEC-OPS-01](open-questions.md#dec-ops-01)で確定する.
1日1回の通常運用では約15世代に相当するが, 回数でなく保存日数で期限を管理する案. 再実行分の世代管理と保管容量は運用設計で定める.
元データの期限が先に到来した場合はバックアップにもその期限を適用し, 15日保持を理由に個人別記録を延命しない.
例: 1月の練習を2月28日にバックアップしても, 個人別出欠は3月1日に削除対象となる.

| ID                                | 対象                             | 保存・復元の方針                                                   | 状態                     |
| --------------------------------- | -------------------------------- | ------------------------------------------------------------------ | ------------------------ |
| <a id="ret-ops-04"></a>RET-OPS-04 | スプレッドシートのバックアップ   | 上記の周期・期間と元データ期限を適用                               | 周期・日数・担当者は確定 |
| <a id="ret-ops-05"></a>RET-OPS-05 | 失敗したバックアップ・作業コピー | 処理失敗後に削除                                                   | 設計案                   |
| <a id="ret-ops-06"></a>RET-OPS-06 | スプレッドシートの版履歴・複製   | 元データの削除期限を満たせる方式を選ぶ                             | 技術検証待ち             |
| <a id="ret-ops-07"></a>RET-OPS-07 | DBサービス管理のバックアップ     | 期限の制御可能範囲を確認                                           | 技術検証待ち             |
| <a id="ret-ops-08"></a>RET-OPS-08 | DDL・RLS・関数                   | 個人データを含めずプロジェクト存続中保持                           | 設計案                   |
| <a id="ret-ops-09"></a>RET-OPS-09 | 復元DB                           | 公開前に保存期限を再適用. セッション・剥奪済み権限を再有効化しない | 設計案                   |

提案する保存・復元要件:

- 単なる上書き同期にせず, 誤更新前へ戻せる複数世代を保存する. テーブル定義・制約・RLS・関数等の復元用マイグレーションも管理する.
- 全テーブルを整合した時点で保存し, 各Appの保存版と復元地点を記録する. 日付・NULL・JSON・先頭ゼロ等の型と値が復元時も一致することを検証する.
- 復元用の秘密情報・認証データ等の扱いは通常の会員データと分けて定義する.
- 失敗を検知し, 最新成功時刻を確認可能にする. 失敗による欠損期間の延長を含め, 許容損失と復旧時間を決める.
- スプレッドシートの版履歴やサービス管理の保存先も追跡し, 削除を制御できない領域があれば要件達成済みとせず保存方法をレビューする.

スプレッドシートだけで全DBの復元要件を満たせるかは未検証. 保存形式や追加の保管先が必要な場合は設計レビューで相談する.

## 毎月1日の共通処理

月初の削除は毎月1日に行う他の処理と合わせて実行する. 正確な時刻と実行基盤は[DEC-OPS-01](open-questions.md#dec-ops-01)で確定する.

処理順序案:

1. 同じ対象月のジョブの重複実行を抑止し, 実行履歴を開始する.
2. 期限対象の練習の集計を確定し, 個人別出欠・関連履歴・title・notesを削除する.
3. 退会者名簿と級履歴を同時に削除する. 必要な級情報の集計利用を先に完了し, 認証APIで対象の紐付けを整理する. 他会員の紐付け・アカウントを連鎖削除しない.
4. 解除済み紐付け・指定の変更履歴を, 上表の条件に従って削除する.
5. バックアップ内の期限対象情報にも削除を適用し, 処理単位の完了・失敗件数を記録する.

バックアップ, ログ, 実行記録, セッションは個別の周期・期限を守り, 月次処理にまとめることを理由に遅らせない.
各Appの対象行は所有Appの運用APIで削除し, 月次処理は実行順と完了を管理する. DBとバックアップをまたぐ削除は一括トランザクションにできないため, 工程別に冪等に再開する. 一部失敗を全体成功として報告しない. App境界と認可は[全体設計](architecture.md)を参照する.
