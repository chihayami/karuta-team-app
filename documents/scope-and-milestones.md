# スコープとマイルストーン

## 設計思想

- 少人数開発を前提に, 各Appと公開契約を理解すれば変更できる大きさに分ける. 全体の内部仕様の理解を個別開発の前提にしない.
- 認証・ポータル・名簿・練習を独立させ, 大会参加希望と大会班も別Appとする. 固有仕様・テストは各App内に置く.
- 単体テストと結合テストを用意する.
- ランニングコスト0円を要件とする. 想定利用量と無料枠の適用可否は別途確認する.
- マジックナンバーを避け, 業務上の値には名前と定義を与える.
- UIはシンプルで一貫性を持たせる.
- ライブラリは採用時点でサポート対象となっている最新の安定版を使用する. Next.js 14への固定は行わない.
- 団体は非営利の会員活動. サービスの無料枠の適用可否は別途確認する.
- 会員約150名, 練習1回最大40名を想定し, おおむね倍の規模に耐えられる設計とする. 同日複数練習と同時アクセスを考慮する.
- DEIに配慮し, 家族構成や性別についてステレオタイプ的な記述を避ける.

## リリース範囲

初回リリースでは, ポータル・練習出欠・名簿管理を一通り使える状態にすることとする.
開発版は[MIL-SYS-03](scope-and-milestones.md#mil-sys-03)から段階提供し本番後も維持する. 詳細は[開発版仕様](development-environment.md)を参照.
大会申込・大会班・会計班は後続リリースとする. 後続機能の業務ルールも失われないよう別文書に記録する.

| 領域             | 要件                                                                                                             | 詳細化する事項                                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 認証・アクセス管理 | ログイン, 多対多の家族紐付け, 登録後ロック, 権限付与・剥奪, LINE変更 | 初回自己申告と事後確認. 承認制にしない. 詳細は認証App仕様 |
| ポータル | 各Appへの入口 | 認証Appと分離し, 業務データを所有しない |
| 練習出欠         | 前日24時締切, 締切後は専用メールへ案内・担当者のみ訂正可能, 満員後も通常登録・超過人数表示, 外部参加・見学・体験は属性のみ | 通知の採否, 閲覧範囲                                                                                                                                 |
| 名簿管理         | Supabaseを正本とし, 指定の名簿管理者が会員登録・編集・休退会・昇級・履歴・取込出力を扱う. 昇級登録の権限を分離             | 項目・入力条件, 変更申請はアプリ全体のスコープ外, 移行元と移行手順                                                                                   |
| 大会参加希望 | 後続リリース. 一般会員向けに独立したApp | 希望入力・変更・取消, 大会班への受渡し |
| 大会班 | 後続リリース. 班作業向けに独立したApp | 現行データ移行, 受付・確定名簿・戦績・集計, Gmail連携 |
| 会計班           | 後続リリース. 送金実施はプロジェクトのスコープ外                                                                           | 入金管理等の業務範囲, 送金状態の参照・更新との境界                                                                                                   |

初回の練習出欠・集計の対象と除外機能は[練習要件](../app/practice/docs/requirements.md), 保持対象と削除期限は[保存期限](data-retention.md)に従う. 大会の集計は後続で定義する.
待機列・自動繰上は初回対象外として確定. 満員後も通常の参加登録として受け付ける.
予備会場は初回対象外. 家族一括登録は初回必須としないが, 家族の各会員を個別に代理操作できることは必要.
募集中の参加者一覧は, 利用資格のあるログイン済み全員へ自由記述の備考も含めて開示する. 未ログイン公開は将来も対象外. 自己申告は名前検索とし, 1つのLINEアカウントに最大5名を紐付ける.
詳細は[初回リリース仕様](initial-release.md)に記載する.

## 構成案: 提案

[ミニアプリ全体設計](architecture.md)に従い, 公開APIを通して連携する. Supabaseは共通アカウントで管理し, 開発・本番は別プロジェクトとする. 各環境内でglobal/localのテーブルと所有者を分ける. 実行環境とデプロイの単位は先行実証で判断する. 認証データ・会員データは所有Appが管理し, 共有テーブルとして扱わない.
Supabaseを利用し, LINE認証結果からDB認可へ接続する方式とRLSを設計する.
名簿の正本とバックアップは分離する. 保存方式・周期・期限・担当者と技術検証対象は[保存期限](data-retention.md#バックアップと復元)に記載する.
ロールは操作権限の集合とし, 会員への代理操作権限と管理権限を分離する.

## 文書化計画

1. 初回スコープと名簿の正本を決める.
2. ポータル・練習出欠・名簿管理の操作と権限を定義する.
3. 通常処理・例外処理・受入条件を定義する.
4. データ設計, 外部連携, 無料運用, バックアップと復旧を設計する.
5. テスト・移行計画と実装計画をレビューする.

[MIL-SYS-01](scope-and-milestones.md#mil-sys-01)では運用詳細, データ辞書, 無料運用・認証・復元の前提を確定する.

## 検証方針: 提案

- 単体テスト: 締切, 対象級, 状態遷移, 出場カウント等の業務判定.
- 結合テスト: DB制約, RLS・認可, 家族代理操作, 同時更新, 名簿更新と出欠の整合性.
- E2Eテスト: 初回紐付け, 家族分の出欠登録, 管理者による名簿・練習管理.
- 移行検証: ID対応, 重複・欠損, 件数, 金額, 状態, 過去のカウント対象判定を照合.
- 運用検証: 復元可能なバックアップ, 無料枠の利用量, サービス停止時の復旧手順, 保持期限経過後の個人別記録の削除と集計保持.

上記の具体的な期待値は, 業務仕様の合意後に確定する.
