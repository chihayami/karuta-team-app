# 開発規約

本規約は人間とAIによる開発に適用する. AIの作業制限は[AGENTS.md](../AGENTS.md), 業務上の期待結果は各仕様書を正本とする. 規約の追加によって既存仕様やテストの期待結果を暗黙に変更しない.

## 規約の構成

| 文書                                             | 正本とする事項                                    |
| ------------------------------------------------ | ------------------------------------------------- |
| [Git運用規約](git-workflow.md)                   | ブランチ, PR, マージ, Git操作の担当               |
| [コーディング規約](coding-conventions.md)        | 命名, 実装の構造, 入出力, エラー, テスト          |
| [セキュリティ開発規約](security-development.md)  | セキュリティレビュー, 検査, skill・拡張機能の導入 |
| [仕様書の管理規則](specification-conventions.md) | 仕様の正本, ID, 参照と変更管理                    |
| [環境仕様](development-environment.md)           | 環境分離, デプロイ, 版の識別, 切戻し              |

## 作業の進め方

1. カレントディレクトリと対象リポジトリを確認する. 作業領域内の全Gitリポジトリについて状態を確認し, 既存変更や競合, merge/rebase途中の状態を計画に記載する. 既存変更の扱いは人間に確認し, 無断で上書き・破棄しない.
2. 関連仕様・契約・テストを読み, 目的, 対象ファイル, 実装方針, 影響範囲, 検証方法, 未確定事項を計画にまとめる. テストの期待結果を変える場合は変更前後と根拠を示す.
3. 計画のレビューを依頼し, 合意した範囲で実装する. 新たな業務仕様の判断やテスト仕様の変更が必要になった場合は計画を更新して相談する. 合意済み事項について同じ確認を繰り返さない.
4. 新機能には自動テストを追加し, 挙動変更には関連する既存テストの修正を伴わせる. 仕様IDと検証内容の対応を維持する.
5. 変更に必要な検査を実行し, 結果を確認する. 失敗を回避するために検査を無効化したり, 期待結果を無断で書き換えたりしない.
6. 変更理由, 最終的な挙動, 検証結果, 残る制約を報告する. PRと本番反映はGit運用規約・環境仕様に従う.

文書の整形と業務仕様の変更は区別する. 無関係な全体整形や依存更新を混ぜず, 1つのPRで目的と影響を説明できる範囲にする.

## 検証と完了条件

現在はWeb基盤・環境設定検証・版表示とその実行可能なテストを実装済み. 型チェック・lint・テスト・ビルドのコマンドは[ローカル開発手順](local-development.md)に記載する. 業務機能・DB結合・LINE実機のテストは未実装であり, 利用できる検査と後続工程で追加する検査を区別する.

| 変更                        | 必要な検証                                                                                    |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| 文書のみ                    | `python3 scripts/check-docs.py`, `npm run check:md`, 仕様・契約・リンクのレビュー             |
| アプリ本体の追加・変更      | 型チェック, lint, 対象の単体・結合テスト, 関連するE2E, ビルド. 実装着手時にコマンドを定義する |
| 認証・認可・公開API・DB変更 | 上記に加え, 契約適合性, 拒否系, 権限境界, データ整合性の検証                                  |
| 環境更新・GASプッシュ       | [環境仕様](development-environment.md)の検証・反映条件. GAS固有の操作手順は実装時に具体化する |

commit前の必須セキュリティレビューは[運用条件](security-development.md#commit前の必須レビュー)に従う. hook・レビュー実行処理を変更した場合は `npm run test:tooling` も実行する.

Markdownは変更したファイルを整形してから全体の確認を行う. 既存ファイルの整形不備が見つかった場合は今回の変更によるものか区別し, 無関係な一括修正を行わない.

完了報告には実行した検査と結果を記載する. 未実装・未実行・失敗を成功として扱わず, 未実行の理由と受入判断への影響を示す. 文書のみの変更に, アプリ機能の自動テスト追加は要求しない.

PRには目的, 変更内容, 関連仕様, テスト結果, セキュリティ・移行・運用への影響を必要な範囲で記載する. レビュー担当者が実際の差分と検証結果を確認してからマージする. AIの自己レビューだけで人間のレビューを代替しない.

## 規約の変更

規約の変更も計画レビューの対象とする. 既存ルールと衝突する場合は, どの正本をどう変更するか明示して合意を得る. skillや拡張機能の説明だけを根拠としてAIの権限を広げない.
